# ADR-0004: API style and documentation

Status: accepted (M0, October 2026)

## Context
API-first: the web app uses the same documented API as future mobile clients and integrations; business logic does not depend on the frontend (`../requirements.md` § API-First Architecture).

## Options considered
- **REST/JSON with an OpenAPI contract generated from code (FastAPI)** — one source of truth, interactive docs, client generation possible.
- **GraphQL** — flexible queries, but more moving parts and less common for self-hosted tools; no clear benefit at this size.
- **Hand-written OpenAPI first** — keeps spec and code in two places.

## Decision
- REST over JSON. The **OpenAPI document generated by FastAPI is the contract**: `/api/openapi.json`, interactive docs at `/api/docs`.
- Versioning by path: business endpoints under **`/api/v1/...`**; a breaking change introduces `/api/v2` while `/api/v1` stays until clients migrate. Operational endpoints are unversioned: **`/api/health`** (liveness + database check).
- Everything outside `/api` is the static web app (SPA fallback to `index.html`).
- Money and quantities are serialized as **decimal strings** in JSON (never JSON numbers), consistent with ADR-0011.
- Errors use a consistent JSON body (`detail` plus a machine-readable `code`), defined in M2.

## Consequences
- Easier: frontend types can be generated from the OpenAPI document; contract tests in CI.
- Harder: decimal strings need explicit parsing in clients (documented in the API).
