# Decision Log

All decisions below were taken during V1 requirements definition (October 2026) and are **accepted**. D-33 onwards record the resolutions of the V1 requirements review (October 2026).
Other documents are the detailed source; this log explains *what was decided and why*.
To change a decision, add a new row that supersedes the old one (do not delete history).

## Scope

| ID | Decision | Rationale |
|---|---|---|
| D-01 | **Custom assets are out of V1.** | Need manual pricing, irregular price series and a dedicated UI. Listed instruments cover the target use case. |
| D-02 | **Cryptocurrencies held directly are out of V1.** Listed crypto ETC/ETN products are normal instruments (type `ETF`). | Different data sources and logic (wallets, crypto-to-crypto swaps). |
| D-03 | **One cash currency per account.** A broker with several cash currencies is modelled as several accounts. | Keeps cash, cost basis and valuation simple. |
| D-04 | **Transfers between accounts are out of V1.** To move holdings, enter a BUY on the new account with `affects_cash = false` and the original average cost. *Refined by D-47.* | See D-08. |
| D-05 | **Corporate actions in V1 = stock split and reverse split only** (`STOCK_SPLIT`). The generic `CORPORATE_ACTION` type is removed. Mergers, spin-offs, conversions are V2. Until then: SELL + BUY; importers flag them as unsupported. | Only splits have fully defined rules. |
| D-09 | **Performance metrics in V1: absolute return (€) and percentage return only.** Annualized return, XIRR and TWRR move to V2 (introduced together). | Fewer edge cases, results verifiable by hand, avoids misleading numbers on partial histories. |
| D-31 | **Geographic allocation is V2.** Best/worst performers are ranked by unrealized % on open positions. | Free providers rarely provide ETF composition data. |
| D-13 | **Account-level expenses (stamp duty, Tobin tax, custody fees) have no dedicated type in V1.** They are entered/imported as `WITHDRAWAL` with a note; the importer keeps the broker's original type in metadata so V2 can convert them automatically. | Keeps cash aligned with the broker without a new type. They do not affect returns in V1 (known limitation). |
| D-28 | **PDF statements ("contabili") attached to transactions are V2.** V1 only reserves `/data/attachments` and makes the backup an archive with a manifest. | Cheap to prepare now, expensive to retrofit. |

## Transactions and editing

| ID | Decision | Rationale |
|---|---|---|
| D-06 | **Editing/deleting a transaction is accepted if the replayed ledger never has negative quantity.** Otherwise it is rejected with the first conflicting transaction. Negative cash is only a warning. Derived data is recalculated after every insert/edit/delete. | Avoid blocking users with incomplete histories while keeping positions valid. |
| D-06b | **No deadlocks.** The product must offer: atomic edit of a transaction (validated on the final state), bulk edit of several transactions validated together, and "delete all transactions of an asset in an account". | Every invalid situation must be fixable from the UI. |
| D-07 | **Deleting is a real delete** with an entry in the internal audit log. | Backup/export already allow recovery; a recycle bin adds complexity. |
| D-08 | **No `INITIAL_POSITION` type.** `BUY`, `SELL`, `DIVIDEND`, `COUPON` have an `affects_cash` flag (default true). A guided flow "Add holdings I already own" creates BUYs with `affects_cash = false`. | Allows full history reconstruction, real dates and lots, and CSV import with or without cash flows. |
| D-14 | **Transaction date = operation date.** The value (settlement) date is kept as metadata. Same-day ordering is deterministic (see domain-rules §4). *Value date: superseded by D-48. Ordering: refined by D-45.* | Verified on real broker exports: only operation date keeps cash non-negative. |
| D-15 | **Cost basis is stored in account currency**, as actually paid. | Gain includes the FX effect, like the broker shows. |
| D-32 | **Exact decimal arithmetic everywhere; quantities support at least 8 decimals.** No binary floating point for money or quantities. *Refined by D-68.* | Correctness; cheap now, costly later. |

## Metrics

| ID | Decision | Rationale |
|---|---|---|
| D-10 | **Percentages:** unrealized % = unrealized € / cost basis of open positions; realized % = realized € / cost basis of the quantity sold (lifetime). Income (dividends/coupons) is shown in € only. *Refined by D-41.* | Each percentage has a simple, hand-verifiable base. |
| D-11 | **Invested capital = cost basis of open positions.** Cash is part of portfolio value but is excluded from returns. | The user wants the return on invested money, not on idle cash. |
| D-12 | **Every gain is shown gross and net of taxes.** Taxes are *recorded* from broker data, never *calculated*. Unrealized gain is the same gross and net (no estimated tax). The dashboard highlights the net figure. | Matches what the investor really kept. |
| D-17 | **Bonds:** quantity = nominal value; price = % of nominal; valued at clean price (accrued interest not included). *Refined by D-43.* | Standard quoting; limitation is disclosed in the UI. |
| D-18 | **Accrued interest paid and taxes are fields of the transaction** (`accrued_interest_paid` on BUY; signed `taxes` on BUY and SELL; `taxes` on DIVIDEND/COUPON). Capital gains tax is a field of SELL, not a separate transaction. *Refined by D-42 and D-43.* | Importers can attach broker side-rows by order reference; per-asset net figures work. |
| D-19 | **Bond maturity/redemption in V1 is entered as a SELL at 100% of nominal.** | No real redemption sample exists yet. |

## Review resolutions (V1 requirements review)

| ID | Decision | Rationale |
|---|---|---|
| D-33 | **Restates D-21b.** The application gives the Administrator no UI or API to read other users' portfolios, but there is **no cryptographic isolation**: whoever has access to the server, the `/data` volume or a backup can read the data. Backup passphrase encryption stays optional but is recommended; the UI and the README say so. | Honest privacy statement; per-user encryption is out of proportion for V1. |
| D-34 | **Restore is possible only from the first-run setup wizard**: the choice "Restore from backup" replaces "Create first administrator". "Empty instance" = no users exist. No restore into an instance that already has users in V1. | Removes the contradiction between "empty instance" and "the Administrator restores from the UI"; merging is the risky part (D-22). |
| D-35 | **Prices and asset visibility.** Provider prices are shared across users; manual prices belong to the user who entered them and never affect other users. Each user sees only the assets they use or added; asset search never reveals which ISINs other users hold. Provider-resolved assets are shared reference data; manually created assets (D-37) are private to their creator, so the same ISIN may exist once as a shared asset and once per user as a private one. | One user's manual price or hand-typed metadata must not change another user's figures, and the asset list must not leak holdings. |
| D-36 | **Reporting currency different from the account currency.** Per-account figures are always in the account currency. The aggregated portfolio converts the already-computed account figures at the latest available rate for current values and at each day's rate for the historical series. No historical FX attribution in V1 (e.g. a realized gain is converted at today's rate, not at the rate of the sale day); the limitation is documented in the UI help. | Simple, verifiable, consistent with D-15; attribution needs a dedicated design. |
| D-37 | **Manual asset creation.** When providers cannot resolve an instrument, the user can create the asset by hand (ISIN, name, asset type, quote currency, quote unit). The asset-discovery principle becomes: the user is not required to type metadata **when it can be fetched**. | Many bonds are not covered by free providers; manual entry must not be blocked. |
| D-38 | **App CSV round trip.** The CSV gains `id` (transaction UUID), `metadata` (JSON), `account_currency` and `account_provider`; the column `note` is renamed `notes`. Duplicate detection: by `id` first, then by `external_ref`. `id` is matched only against the importing user's own transactions; an `id` that already exists for another user is replaced by a new one, without revealing anything. Accounts are mapped to existing ones or created from the file in the preview (all created on a fresh instance). A CSV with several accounts creates one import batch per account. | Export → import must reproduce the data without duplicates and without losing the original broker type (D-13). |
| D-39 | **Administrator with a portfolio; account lifecycle.** The Administrator also has Investor rights on their own data. Accounts are editable (name, provider); the cash currency is locked after the first transaction; an account can be deleted (with its transactions) after confirmation, with an audit log entry. Archiving accounts is V2. | In a household the administrator is usually also an investor; deleting a mistaken account must be possible. |
| D-40 | **Single cost-removed formula on SELL:** `cost removed = cost basis × quantity sold / quantity held`, rounded as in `domain-rules.md` §0. The rounded PMC is for display only and is never used in calculations. | Two formulas gave different results once the PMC is rounded. |
| D-41 | **Percentages.** Realized % is defined gross and net, both on the cost of the quantity sold: gross = realized gross / cost removed; net = (realized gross − SELL taxes) / cost removed. Unrealized % is unchanged (D-10). Total gain is shown in € only (gross and net); income stays in € only. | Every percentage keeps a simple base; a total-gain % would need a base that mixes open and closed positions. |
| D-42 | **Where taxes land.** BUY `taxes` are allowed only on bonds (credits on accrued interest or issue discount) and count as **income taxes**. DIVIDEND/COUPON `taxes` count as income taxes. SELL `taxes` count as **realized taxes**, including any withholding on accrued interest received (known simplification: the net total is unaffected). | Removes the E3/E4 ambiguity with one rule per transaction type. |
| D-43 | **New SELL field `accrued_interest_received`** (bonds only, ≥ 0, default 0): it is gross income of the asset, it is part of the cash movement, and it does not affect cost basis or realized gain. | Secondary-market bond sales credit accrued interest; without the field the SELL invariant could not match the broker. |
| D-44 | **Quotes in minor currency units** (e.g. GBX, pence): asset quote unit `MINOR_CURRENCY_UNIT`; the quote currency is the major currency (e.g. GBP) and the price is divided by 100 before FX conversion. | London-listed instruments are quoted in pence; otherwise values would be 100× too high. |
| D-45 | **Same-day ordering:** transactions without `trade_time` first, by type priority (`DEPOSIT`, `STOCK_SPLIT`, `BUY`, `DIVIDEND`/`COUPON`, `SELL`, `WITHDRAWAL`); then transactions with `trade_time`, by time; remaining ties by insertion sequence. | The previous rule did not say how timed and untimed transactions mix. |
| D-46 | **Valuation without a price.** On any day for which an asset has no price on or before that day (never priced, or before its first price), the position is valued at that day's cost basis and flagged "estimated at cost". Charts are never blocked by missing prices; only missing FX makes a total or a chart partial. | Charts must not disappear because one bond has no data source. |
| D-47 | **Transfer workaround (refines D-04):** on the source account a `SELL` with `affects_cash = false` whose `gross_amount` is the exact cost removed (zero fees and taxes, so zero gain); on the destination account a `BUY` with `affects_cash = false` at the same cost. Known limitation: the transfer adds its cost to the realized % base of the source with zero gain. | Moves a holding without inventing a realized gain or a cash flow. |
| D-48 | **`value_date` is a real column of the transaction** (optional, informational), not metadata. Supersedes the "kept as metadata" part of D-14; the transaction date remains the operation date. | It is present in every broker export and is useful for reconciliation. |
| D-49 | **Directa import clarifications.** The option "I did not record the deposits: do not move cash" also skips `DEPOSIT` rows and account-expense `WITHDRAWAL` rows by default (each individually selectable in the preview). An `Acquisto` without an order reference is "not recognized". The asterisk in `Bollo portafoglio titoli*` is a literal character. Importing a Directa file into an account whose currency is not EUR is a blocking error. A merged transaction takes the insertion sequence of its oldest row (last row in file order). | Closes the gaps found in the review without guessing broker behaviour. |
| D-50 | **Milestones.** Basic authentication (setup wizard, login, sessions) and ownership filtering move into M2; 2FA, the admin area and hardening stay in M6. UI mockups are an explicit step (M0.5) before M2. A milestone may span several sessions; never two milestones in one session. | The API must be owner-filtered from the first endpoint; the screens shape the API. |
| D-51 | **Admin area in V1:** users, market data providers, backup/restore, session duration, login lockout thresholds. Trusted proxies for rate limiting are configured by an environment variable (list of networks), not in the UI. | Defines "security settings" and "system configuration"; per-IP limits behind a proxy need trusted forwarded headers. |
| D-52 | **Minor cases.** A DIVIDEND or COUPON on a closed position (quantity 0) is allowed. Cash paid in lieu of split fractions is entered as a SELL of the fractional quantity. | Common real cases that the rules did not state. |

## Calculation engine (M1)

| ID | Decision | Rationale |
|---|---|---|
| D-54 | **Property tests use `hypothesis`** (dev dependency only, pinned exactly, license checked like every other dependency). It is added when the property tests are written, after the maintainer's go-ahead. | ADR-0010 requires property tests for ordering and edits; generated inputs with shrinking find edge cases that hand-picked examples miss. |
| D-55 | **Valuation is part of the M1 engine as pure functions**: prices and FX rates are passed in memory; the engine applies quote units, carry-forward, "estimated at cost" (D-46) and conversion to the reporting currency (D-36). Providers, stored history, the scheduler and the stale-price flag stay in M4. | The §16 examples E3, E4, E11 and E12 need valuation; keeping it pure keeps it testable without a database. |
| D-56 | **Quantity after a stock split** = `quantity × new / old`, rounded to 8 decimals half-even like every other derived division (`domain-rules.md` §0). | One rounding rule in the engine; quantities already support 8 decimals. |
| D-57 | **Percentages are returned by the engine as ratios** (e.g. `0.10000000` for +10%), rounded to 8 decimals half-even; when the base is zero the value is "not available" (`None`), never 0 and never an error. The UI multiplies by 100 and rounds for display. | One representation for all percentages; a zero base has no meaningful percentage. |
| D-58 | **FX conversion rounds once**: the converted amount is rounded to 8 decimals half-even; no intermediate rounding (a cross rate between two non-EUR currencies is not rounded on its own). *Superseded by D-71.* | Avoids compounding rounding errors; consistent with §0. |
| D-59 | **DIVIDEND or COUPON on an asset never held in that account** is accepted **with a warning** (not rejected), because the recorded history may be incomplete. On a position that was held and is now closed it is accepted without a warning (D-52). *Superseded by D-72.* | Do not block users with partial histories, but surface a likely missing BUY. |
| D-60 | **Transaction invariants are checked with exact `Decimal` comparison**, no tolerance (`4889.90` equals `4889.900`; `4889.91` does not). | Amounts come from the broker or the user exactly; a tolerance would hide entry errors. |
| D-61 | **Negative cash is checked at the end of each day**: the warning reports the first date whose end-of-day balance is below zero; a dip inside a day that is recovered the same day does not warn. | Matches §11 ("cash balance at a date = Σ up to and including that date"); same-day order is not a reliable view of the broker's intraday cash. |
| D-62 | **Fields not listed for a type in `domain-rules.md` §2 are rejected** (e.g. `quantity` on a COUPON, `fees` on a DIVIDEND); the §2 table is a closed list. **To revisit in M3**: whether a COUPON may carry the nominal as informational `quantity` when an importer provides it. | Never accept data the rules do not define; the import specs will show whether the nominal is needed. |
| D-63 | **Selling the whole position removes exactly the remaining cost basis** instead of applying the D-40 formula, so a closed position has cost 0 even when the cost has more than 8 decimals. With ≤ 8 decimals the result is identical to D-40. | A closed position must never keep a rounding residue. |
| D-64 | **Missing FX gives a partial total, not an unavailable one.** The affected position's value is unavailable; the account's securities value, total value and unrealized (€ and %, base = cost of the valued positions only) sum the valued positions and carry a `partial` flag. **M2/M5 must show a clearly visible "partial" label next to every total that carries the flag.** | Never invent numbers (§12) but keep the rest of the account visible; the label prevents reading a partial figure as complete. |
| D-65 | **Total gain of a partial account** (gross and net) uses the unrealized of the valued positions only; realized and income do not depend on prices and stay complete. The `partial` flag propagates to the gain figures (same visible label, D-64). *Superseded by D-73.* | Consistent with D-64. |
| D-66 | **Bond average cost:** the engine returns the PMC per unit of nominal in account currency (e.g. `0.976`); the API (M2) multiplies by 100 to show it as % of nominal (`97.60%`), like other display conversions. | The engine has one PMC definition for every asset; display formats belong to the API/UI. |
| D-67 | **Field rules tightened after the M1 review.** (1) The closed list of D-62 also rejects a field given as 0 (`fees = 0` on a DIVIDEND, `accrued_interest_paid = 0` on an ETF BUY): an optional amount that is not given is distinct from 0 and counts as 0 in calculations. (2) `unit_price` ≥ 0; the informational DIVIDEND `quantity`, when given, is > 0. (3) An asset of type `BOND` is always quoted `PERCENT_OF_NOMINAL`, and only bonds use that unit. | A zero in a field that does not exist for the type is still data the rules do not define; negative prices and holdings counts are entry errors; a bond quoted per unit would be valued 100× wrong. |
| D-68 | **Quantities have at most 8 decimals.** A quantity (BUY, SELL, informational DIVIDEND quantity) with more significant decimals is rejected; trailing zeros are accepted (`1.1234567800`). Refines D-32. | Every derived quantity (split, D-56) is rounded to 8 decimals anyway; broker quantities and fund units fit in 8; one scale keeps quantities comparable and lets a full sale match the held quantity exactly. |
| D-69 | **A split that would round a held quantity to zero is rejected** as a conflict (like a negative quantity, §4), naming the split. A split on a closed or never-held position (quantity 0) stays valid. | With D-56 rounding, e.g. 0.00000001 split 1:2 becomes 0 while the cost basis stays: a position with cost and no units would corrupt every later PMC and unrealized figure. |
| D-70 | **Insertion sequence** (`sequence` column of a transaction): an integer **unique per account**, assigned by the app in increasing order when a transaction is created; on import, in the order of the file rows (chronological, D-49 for merged rows); **unchanged** when the transaction is edited, also when its date changes. The engine breaks any remaining tie by transaction id so the replay never depends on input order. | D-45 relies on the sequence but the data model did not define it; a stable sequence keeps an edit from reshuffling same-day transactions. |
| D-71 | **Supersedes D-58. Values are rounded once**: an FX-converted amount is rounded to 8 decimals half-even, with no intermediate rounding (a cross rate between two non-EUR currencies is not rounded on its own). A position value (quantity × price with the quote unit, §2) is rounded once in the same way also when the asset is quoted in the account currency and no conversion happens. | Avoids compounding rounding errors; every value has the same scale (M1 review); consistent with §0. |
| D-72 | **Supersedes D-59. DIVIDEND or COUPON on an asset not held in that account at any time up to its date** is accepted **with a warning** (not rejected), because the recorded history may be incomplete; income dated before the first BUY warns even if the asset is bought later. On a position that was held and is now closed it is accepted without a warning (D-52). | Do not block users with partial histories, but surface a likely missing BUY; the reference date makes the rule unambiguous (M1 review). |
| D-73 | **Supersedes D-65. Total gain of a partial account** (gross and net) uses the unrealized of the valued positions only; realized and income do not depend on prices and stay complete. The `partial` flag propagates to the gain figures (same visible label, D-64). **In the portfolio**, an account whose currency has no rate to the reporting currency is left out entirely (value, cash, realized, income, taxes), so the single portfolio `partial` flag covers every portfolio figure. | Consistent with D-64; one flag keeps the portfolio label simple (M1 review). |

## Data model, API and basic auth (M2)

| ID | Decision | Rationale |
|---|---|---|
| D-82 | **Minimal brute-force protection in M2** (before the configurable lockout of M6). (1) An unknown user, a disabled user and a wrong password get the same 401 `INVALID_CREDENTIALS` in a comparable time (a dummy Argon2 verification when the user does not exist). (2) Failed password checks are counted in memory per key: **username** (case-insensitive) and **client IP** for login, **user** for the password change (current-password check). (3) **Thresholds: 5 consecutive failures per username and per user (password change), 30 per IP.** Past the threshold the key is blocked for 1 minute, and each further failure doubles the block up to 15 minutes (429 `TOO_MANY_ATTEMPTS` with `Retry-After`). (4) An attempt is reserved before the password is checked and counts as a failure unless it succeeds, so parallel requests cannot exceed the free attempts. (5) A success clears the username and password-change counters, never the IP counter; counters are forgotten after 30 minutes without failures; a restart clears them. (6) The client IP is the direct peer: the server does not trust forwarded headers until trusted proxies are configurable (M6). (7) Password checks run outside any write transaction. Details in ADR-0005. | Login and the password change must not be open to unlimited guessing between M2 and M6, also by someone holding a stolen session. **Why the IP threshold is higher:** behind a reverse proxy (the recommended HTTPS setup) every household member arrives with the proxy's address, so an IP threshold equal to the username one would let 5 typos by anyone lock the whole family out; the username threshold carries the protection of each account, the IP one only slows down guessing across many usernames. Known trade-off: anyone can delay a user's login by up to 15 minutes by failing on purpose. In-memory state is enough for one process (ADR-0006). |
| D-83 | **Scope of M2** (refines D-50): the setup wizard creates the first Administrator; login, opaque sessions, the user's own profile and password, and a minimal user-management API for the Administrator (create, reset password, disable, enable) are in M2. 2FA, configurable lockout and session settings, and the admin area UI are M6; backup and restore are M7: `POST /setup/restore` exists and answers 501 `NOT_IMPLEMENTED` (409 `SETUP_ALREADY_DONE` once users exist). | A second user cannot exist without user creation; everything else follows the milestone split of D-50. |
| D-84 | **Derived data is computed on request.** No derived tables: every summary, position and warning is a fresh engine replay of the stored transactions and prices. The rebuild path of §15 is the replay itself. | Simplest correct option at household scale; caches can be added later without changing the API (they are never authoritative). |
| D-85 | **An edit may move a transaction to another account of the same owner** (refines D-70). Both ledgers are validated and the change is accepted only if both pass; the moved transaction keeps its id and gets the next insertion sequence of the destination account (the sequence is unique per account). | Fixing a transaction entered in the wrong account must not need delete + re-create, which later SELLs may block (D-06b). |
| D-86 | **Warnings on a change.** A create, edit, bulk edit or delete returns every warning of the resulting ledger(s), each with `introduced: true|false` (not present before the change, compared on code + date + transaction id). Warnings never reject. | The user sees what the change caused without losing sight of older warnings (M1 review note). |
| D-87 | **Manual prices in M2.** The `prices` table is provider-ready (`source` `PROVIDER` or `MANUAL`, `owner_id` set for manual prices only). A user sets, lists and deletes their own manual daily closes for an asset they can see; for that user a manual close overrides a provider close on the same day (D-35). Providers, scheduler, stale flag and the FX table are M4. | The M2 isolation tests cover manual prices; the table must not change shape when providers arrive. |
| D-88 | **Session expiry defaults:** 7 days without use or 30 days after login, whichever comes first (`PT_SESSION_IDLE_DAYS`, `PT_SESSION_ABSOLUTE_DAYS`); configurable in the admin area in M6. Details in ADR-0005. | D-51 asked for a configurable duration but gave no default. |
| D-89 | **Login identifier = username** (3–32 characters `A-Z a-z 0-9 . _ -`, unique case-insensitively), as in the mockups; a display name is optional. | No mail server, so an e-mail address adds nothing; ASCII keeps the case-insensitive uniqueness exact. |
| D-90 | **Account currency lock** (refines D-39): the currency can change only while the account has no transaction; deleting them all unlocks it (409 `CURRENCY_LOCKED`). Account deletion requires `confirm_name` equal to the account name in the request: the API enforces D-77, not only the UI (422 `CONFIRMATION_MISMATCH`). | The lock protects stored amounts, which are in the account currency; an empty account has nothing to protect. |
| D-91 | **Editing assets.** Users create private assets only (D-37); shared assets are read-only to users (403 `ASSET_READ_ONLY`) and created by providers from M4. Name and ticker are always editable; type, quote currency, quote unit and ISIN only while no transaction uses the asset (409 `ASSET_IN_USE`); an asset can be deleted only when unused, together with its manual prices. **One private asset per ISIN and user** (409 `ISIN_ALREADY_USED`, also a partial unique index); the ISIN stays optional. The link for shared assets a user "added" without using them (D-35) is designed with asset search in M4. | Structural fields change the meaning of stored amounts; two private copies of one ISIN would split a holding. |
| D-92 | **Not found, never forbidden.** Another user's resource, and an admin endpoint called by a non-administrator, answer 404 `NOT_FOUND`, indistinguishable from a missing one; no session is 401 `NOT_AUTHENTICATED`. Errors use one body `{detail, code, ...}` with stable codes (ADR-0004). `backend/tests/test_route_matrix.py` classifies every route of the OpenAPI document (public, self, owned, admin) and fails on an unclassified one. | A 403 would confirm that an id exists; the matrix keeps the rule enforced for every future endpoint (D-33). |
| D-93 | **Temporary passwords and account safety.** Until a temporary password is changed, every endpoint except `GET /me`, the password change and logout answers 403 `PASSWORD_CHANGE_REQUIRED`. Changing the password ends the user's other sessions; an administrator reset or disable ends all of them. The Administrator cannot disable themself (409 `CANNOT_DISABLE_SELF`) nor the last active administrator (409 `LAST_ADMINISTRATOR`). Recovery without e-mail: `python -m portfolio_tracker reset-password <username>` in the container prints a temporary password once. | Completes D-78; prevents locking the instance out of administration. |
| D-94 | **Write safety.** Cookie-authenticated non-GET requests must carry `X-Requested-With: portfolio-tracker` (CSRF, ADR-0005). Every write runs in one SQLite transaction started with `BEGIN IMMEDIATE`, so validation and persistence cannot interleave with another write; password hashing never runs inside it. Currencies are validated against a static ISO 4217 list in code. | One process and one SQLite file (ADR-0002, ADR-0006): the database lock is the simplest correct serialization. |
| D-95 | **Valuation day of current figures** = the later of today (UTC) and the date of the user's latest transaction, the same day for every account and for the portfolio. Every stored transaction therefore counts, also one dated after today. | Avoids figures that silently ignore a transaction (e.g. entered just after midnight in Italy, still "tomorrow" in UTC), with no time-zone setting. |
| D-96 | **Future-dated transactions** are accepted with a `FUTURE_DATE` warning (date = the transaction date), returned on every change with the `introduced` flag of D-86 and in the account summary. "Today" is the UTC date (domain-rules §4). | A mistyped year becomes visible at once without blocking legitimate entries. |
| D-97 | **Derived-read conventions** (`/accounts/{id}/summary`, `/accounts/{id}/positions`, `/portfolio/summary`): amounts are decimal strings in the account currency (portfolio: reporting currency); percentages are ratios (`0.1` = +10%), `null` when the base is zero (D-57); a bond PMC is returned as % of nominal (D-66). The gain of a position (gross = unrealized + realized gross + income gross; net = gross − taxes) is `null` when its value is unavailable for a missing FX rate. Until the FX table exists (M4), a position quoted in another currency than its account is unavailable (account `partial`, D-64) and an account in another currency than the reporting one is left out of the portfolio (`partial`, `unavailable_currencies`, D-73). | Never invent numbers (§12); ratios keep the display format in the UI; the flags tell the UI to show the "partial" label. |
| D-98 | **Findings of the M2 review.** (1) A transaction can move only to an account **with the same currency** (refines D-85): otherwise 409 `CURRENCY_MISMATCH`; the user deletes it and enters it again with the broker's amounts in the other account. (2) Decimal strings in requests have **at most 15 integer digits** (and 20 decimals): larger values are 422 `REQUEST_INVALID`. (3) Setting and deleting a manual price is audited (`price.set`, `price.deleted`, before/after = asset, day, close), as every real delete (D-07). | (1) Amounts are in the account currency (D-90): reinterpreting them in another one would silently change their value. (2) 999 trillion is far above any real figure, and products of two inputs stay inside the engine precision (60 digits); before, an absurd input was stored and then made every summary of that user fail. |

| ID | Decision | Rationale |
|---|---|---|
| D-99 | **Unconfirmed Directa movement types are "to review".** A type whose mapping is documented but whose meaning the broker has not confirmed (today only `Rit.credito disaggio`, mapped as a tax credit: file +x ⇒ BUY `taxes` −x) is mapped as documented, but the **whole transaction** it belongs to is listed under "to review" and is **not selected** by default; it is imported only if the user selects it. The preview gives a specific reason (code `UNCONFIRMED_MOVEMENT_TYPE` with the original type and the mapping, e.g. "Rit.credito disaggio is unconfirmed; mapped as a tax credit"). When the broker confirms the meaning, the type moves to the plain verified list (one line in `import/directa.md` plus a decision row). | Never guess (CLAUDE.md rule 5) without blocking the import: the user sees the hypothesis and the amounts and decides. |
| D-100 | **Stateless preview and confirm.** Nothing is stored before confirmation. The preview returns the full result and a **fingerprint** (SHA-256 of the canonical preview result, computed from the file, the chosen account(s), the "do not move cash" option and the new-asset choices). Confirm sends the same file again with the same inputs, the selected rows (by stable row keys from the preview) and the fingerprint; the server parses and previews again and answers 409 `IMPORT_PREVIEW_STALE` if the fingerprint differs (e.g. another import or an edit changed duplicates or warnings meanwhile). Changing the account, the option or an asset choice means calling the preview again. | The file is "not kept" (mockup 07); no draft table, expiry or cleanup; the user confirms exactly what they saw. |
| D-101 | **Upload and untrusted-input limits.** The file travels as a base64 field of a JSON body (no multipart). Checked in this order, each before the next step runs: base64 length ≤ ceil(10 MB × 4 / 3); decoded size ≤ 10 MB; for `.xlsx`, at most 100 zip parts, no encryption, and declared uncompressed sizes capped per part and in total (Python's zip reader never returns more than the declared size): **sheet part 16 MB, shared strings 4 MB, every other part 1 MB, total 24 MB**; then a streaming pre-scan of each sheet in near-constant memory refuses a row with more than 64 cells (or 512 elements), more than 10,000 elements outside rows, or more rows than the cap; then openpyxl reads the rows and **stops** at the row cap (xlsx 10,000 data rows; CSV 20,000 rows). One xlsx is parsed at a time in the process (a lock). *Sizing (Opus review of M3, checkpoint C):* real Directa exports take about 400-440 bytes per data row in the sheet part (shared strings), the synthetic fixture about 650 (inline strings); budgeting 800 bytes per row, 10,000 rows are 8 MB, so 16 MB is a 2x margin (tested). Shared strings: about 4 distinct strings of about 40 bytes per row = 1.6 MB, capped at 4 MB. Other parts are a few KB in real files. The pre-scan exists because openpyxl builds a whole row before applying its column limit: before it, an 80 KB upload with one 9 MB row took about 250 MB and 16 s while staying inside the size caps. Exceeding a limit is 413 `IMPORT_TOO_LARGE`; a malformed file is 422 `IMPORT_FILE_INVALID`. The xlsx reader is **openpyxl** (read-only, values only) hardened with **defusedxml**, which openpyxl uses automatically and which refuses entity expansion, DTDs and external entities; the reader refuses to run if openpyxl would use another parser (defusedxml missing or disabled, or lxml installed). | A user's upload is untrusted input: a zip bomb or huge XML must not exhaust memory. JSON keeps one strict schema per request; the limits are well above the reference size (5,000 transactions per user, Directa files cut at 3,000 rows). |
| D-102 | **Asset type of a new ISIN on import (no provider yet).** `BOND` is proposed only on evidence in the file: a Directa ticker starting with `M.` (`import/directa.md` §1) or a bond-only row for that ISIN (`Cedola obb.`, `Ratei pass.obb.`, `Rit.ratei pass.obb.`). Otherwise no type is proposed and confirmation is refused (422) until the user chooses one. Quote currency EUR (every verified Directa row is EUR), quote unit from the type (`BOND` → `PERCENT_OF_NOMINAL`, otherwise `CURRENCY`); the user can change both. The asset is created **private** (D-37) from the ISIN and the file description. | Never guess a type from weak hints (ISIN country), but do not make the user re-state what the file already proves. Providers and shared assets arrive in M4. |
| D-103 | **App CSV version 1.** First column `format_version`, value `1` on every row, always written by the export. On import a missing column means version 1 (hand-made files); another value, or mixed values, is 422 `IMPORT_FORMAT_VERSION`. Rows breaking a field rule are listed with their line number and cannot be selected; the selected rows are validated as a whole with the existing ledger, and a quantity conflict refuses the confirmation (409 `QUANTITY_CONFLICT`, naming the line). | Standard CSV that survives spreadsheet editing; every row says how to read it; a breaking change can introduce version 2. |
| D-104 | **Manual entries overlapping an import.** Duplicates are matched only by `id` and `external_ref` (D-38, `import/directa.md` §6). When the target account has transactions **without** `external_ref` dated inside the file's date range, the preview shows one account-level notice (`MANUAL_OVERLAP`, with count and range): "check for double entries". No per-row matching. | Date, asset and quantity are never identity (two identical same-day orders are a verified case); the notice still catches the common mistake. |
| D-105 | **Numbers in Excel cells.** Excel stores numeric cells as binary doubles (the real exports write e.g. 17 significant digits). The reader converts each numeric cell to the **shortest decimal string that round-trips** to the same double, then to `Decimal`, with no other rounding. Guards, which make the row **ambiguous** (not imported): an `Importo euro` with **more than 2 decimals** after conversion (this check applies **only** to the euro amount column: it is a cash movement in EUR); a `Quantità` with more than 8 decimals (the general quantity rule, D-68); a text cell where a number is expected. *Added after the Opus review of M3 (checkpoint C), the API limits apply to Directa cells too:* a number with 15 or more integer digits (`NUMBER_TOO_LARGE`, D-98); a protocol or order reference longer than 64 characters (`NOT_A_CODE`); an ISIN that is not valid ISO 6166, check digit included (`NOT_AN_ISIN`; ISINs are upper-cased like the API); a ticker over 32, a description over 200 or a movement type over 100 characters (`TEXT_TOO_LONG`). The file has no price column: `unit_price` is derived (`import/directa.md` §3) and follows the rounding of `domain-rules.md` §0. | The shortest round-trip string is exactly the figure the broker printed; the guards catch a file that is not what we verified. Binary floats never reach a calculation (CLAUDE.md rule 2). |
| D-106 | **No quantity on COUPON** (D-62 confirmed, the M3 revisit). Directa income rows carry quantity 0, which the importer ignores; the app CSV rejects a COUPON quantity like the API. A screen may show the held quantity as derived information (mockup 08). **Quantity on Directa rows:** a non-zero `Quantità` is expected on the **main row of an order** (`Acquisto`; `Vendita` and split rows once real samples verify them, until then they are not recognized, D-20) and only there. On a **side-row** (`Commissioni`, `Ratei pass.obb.`, `Rit.ratei pass.obb.`, `Rit.credito disaggio`), an income or withholding row (`Cedola obb.`, `Rit.cedola obb.`, `Incasso dividendi italia`, `Ritenuta dividendi italia`), a deposit or an account-expense row, a non-zero quantity makes the row ambiguous. | No importer provides the nominal on income; the held quantity is already derivable. Quantity belongs to the row that moves the position, never to a row attached to it. |
| D-107 | **CSV export ships in M3**: `GET /api/v1/transactions/export.csv` (all the user's transactions, or one account), every column of `import/app-csv.md`, `format_version` first. M7 adds the fresh-instance round-trip check. | Import and export are one format (D-38); the round trip must be tested where the format is built. |
| D-108 | **Inconsistent Directa rows are never imported.** Each case is listed as an ambiguity with its rows (not selectable): one order reference with different operation dates **or different value dates** (stricter than the first wording: never guess which value date is right; none in the verified exports) or different ISINs; a side-row (`Commissioni`, `Ratei pass.obb.`, `Rit.ratei pass.obb.`, `Rit.credito disaggio`) whose order has **no main row** (no `Acquisto` or `Vendita`) in the file; an order containing a row of an unrecognized type; the same protocol twice in one file; an order whose amounts break a field rule of `domain-rules.md` §2, checked **on every `Acquisto` row** (each must be negative, so −10 and +3 never merge into a purchase of 7) and on the sums of the side-rows (the BUY invariant itself holds by construction, since `total_amount` = −Σ amounts of the order); **an income row (dividend or coupon) that may have lost its withholding** (`PAIRED_ROW_REJECTED`): a withholding row of the matching kind, with the same date and ISIN as far as they can be read, was rejected or sits inside an order, and the income is not paired by consecutive protocol: importing it would record taxes 0. *The last three points were added after the Opus review of M3 (checkpoint C).* Not-recognized rows without an order reference stay "not recognized" (D-20). | The spec was silent on these cases; importing part of an order would put wrong cash and cost in the ledger. |
| D-109 | **One audit entry per import.** Confirming an import writes one `import.confirmed` entry (batch id, account, source, file hash, counts, ids of the assets created) instead of one `transaction.created` per row; each transaction links to its batch (`import_batch_id`). Later edits and deletes are audited per transaction as usual. | A 3,000-row file would otherwise add 3,000 entries; the batch link keeps every transaction traceable. |
| D-110 | **CSV export is safe to open in a spreadsheet.** Applies to the **text columns** `account`, `account_provider`, `ticker`, `asset_name`, `external_ref`, `notes` and `metadata`, never to numeric, date or code columns (a negative amount such as `-2.44` is written as is). Export: a text cell that, after any leading apostrophes, starts with `=`, `+`, `-` or `@` gets one more leading `'` (`=x` → `'=x`, `''=x` → `'''=x`). Import: the exact inverse, i.e. one leading `'` is removed only when the rest of the cell would itself get one on export (`'=x` → `=x`, `'''=x` → `''=x`). A cell that starts with apostrophes not followed by a formula character (e.g. `'hello`, `''hello`) is written and read unchanged. Tab and carriage return are not treated as formula starts. Round-trip tests cover each case. *Revised twice in M3: "removed only when the next character is = + - @" could not read `''=x` back (step 4), and one apostrophe was not enough for two or more (Opus review, checkpoint C); the protected columns were extended from notes, asset name and metadata to every text column (maintainer, checkpoint C).* | Names, references and notes are free text: without escaping, opening the export in Excel or LibreOffice could run a formula (CSV injection). The inverse rule keeps every value round-tripping exactly. |
| D-111 | **App CSV carries the asset definition** in `asset_type`, `asset_quote_currency`, `asset_quote_unit` (written by the export; used on import only to create an asset that does not exist; ignored, with a warning on mismatch, for an existing one). | Without them a round trip into a fresh instance (M7) would make the user re-type the type, currency and unit of every asset. |
| D-112 | **"Do not move cash" also applies to the app CSV**, as for Directa (D-49). **Option off:** every row keeps its own `affects_cash` value (an empty cell means `true`). **Option on:** every BUY/SELL/DIVIDEND/COUPON row is imported with `affects_cash = false`, whatever its cell says; DEPOSIT and WITHDRAWAL rows (which have no such flag, domain-rules §3) are skipped by default and individually selectable. | Mockup 07 offers the option for every format and `requirements.md` states it for every import; one behaviour is simpler to explain. |
| D-113 | **Import service details (M3, step 6; proposals the maintainer can change).** (1) **Already present** lines (category `DUPLICATE`) are listed but **cannot be selected**: importing them again would count them twice; a user who really wants a second copy enters it by hand.
