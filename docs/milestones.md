# Implementation Milestones (V1)

A milestone may span several short Claude Code sessions, but a session never covers two milestones (D-50). Each session follows this cycle: **plan (plan mode) → approval → implementation → tests → commit → verification by the maintainer**. A milestone is done when its "Done when" items pass and the docs are updated if a decision changed. Start a fresh session for each new milestone; `CLAUDE.md` and `docs/` carry the context.

Suggested model use: strongest model for M0 architecture decisions and M1/M2/M7 (calculation, data model, backup); a lighter model is fine for UI and routine CRUD.

## Notes
- Do the real-data checks (import of the maintainer's own exports, price coverage of real ISINs) locally with files under `private/`; never commit them or their figures.
- Anything not specified in the docs: stop and ask, then record the answer in `docs/decisions.md`.
- Deferred from the M1 review (October 2026):
  - **M2:** an edit that moves a transaction to another account touches two ledgers; validate both with `apply_changes` and accept only if both pass. `Outcome.ledger.warnings` covers the whole ledger: decide how to show warnings introduced by a change versus those already present. *Done in M2 (D-85, D-86).*
  - **M5:** the historical value series needs daily snapshots built in one pass (today each day is a separate `replay(as_of=day)`, cost days × transactions); design it against the performance targets in `requirements.md`.
- Noted from the M2 auth review (checkpoint B, October 2026), not fixed in M2:
  - **M6:** issue a new session token when the password changes (today the current session keeps its token); on login, revoke a session already present in the incoming cookie; the "plain http" cookie warning may fire wrongly behind a TLS proxy until forwarded headers are trusted (logged once only).
  - **M4:** a cleanup job for expired sessions (they are rejected but no longer deleted on access).
  - **When users can be deleted (V2, "delete my data"):** `audit_log.actor_user_id` has no `ON DELETE` rule; decide whether audit entries keep a dangling id, are anonymised, or block the deletion.
- Noted at the end of M2 (October 2026), not done in M2:
  - **M4:** the FX table and provider make foreign-quoted positions and other-currency accounts complete (today `partial`, D-97); add the "value in the reporting currency" line of an account (mockup 13), the stale-price flag and a "manual price" marker on positions. With the shared-asset link (D-91): a user's manual prices on a shared asset they no longer use are not reachable through the price routes (the asset is no longer visible) and would value a later purchase again; let the user see and delete them, or remove them when the last use goes.
  - **M5:** a holdings view aggregated across accounts (mockup 02, "All accounts": one row per asset with total quantity and average cost, D-74) needs FX for accounts in different currencies; design it with the historical series.
  - **M6:** the isolation test of the admin area must state explicitly that an administrator password reset (D-78, D-93) lets the Administrator log in as that user; the user notices (locked out, temporary password) but nothing prevents it. Decide whether to document it only (no cryptographic isolation) or to add a safeguard (e.g. a notice to the user at next login).
